# TenderIQ data set

Layout and conventions follow **Section 9** of the scope document.

```
data/
  notifications/   real tender notifications (Section 9.1)
  vendors/         synthetic vendor bids, generated (Section 9.2)
  corrigenda/      real or synthetic amendments (Section 9.1 step 3 / 9.2.4)
  reference/       sample RFP responses for retrieval testing ONLY (Section 9.2.3)
  samples/         generated fixtures used by the test suite — not evaluation data
  tracking_notifications.csv   Section 9.4, Tab 1
  tracking_vendors.csv         Section 9.4, Tab 2 — this is the answer key
```

## Naming

- Notifications: `NOTIF_<sector>_<serial>.pdf`
- Vendor bids: `VENDOR_<notification_id>_<serial>.pdf`
- Corrigenda: `CORRIG_<notification_id>_<serial>.pdf`

## Keep these separate

`reference/` holds publicly available sample proposals used to give the vector
store varied prose (Section 9.2.3). They have **no** compliance label and must
never be mixed into the labelled evaluation set — doing so silently corrupts the
elimination precision/recall numbers in Section 10.

`samples/` holds synthetic fixtures generated by `backend/tests/doc_factory.py`
for the test suite. Also not evaluation data.

## Ground truth comes first

Section 9.2.2 step 3 is not optional ordering advice: write the intended
`vendor_id, intended_status, intended_reason` row into `tracking_vendors.csv`
**before** generating that vendor's document. Generating first and labelling
afterwards produces files with no answer key, and Section 10's evaluation
chapter has nothing to measure against.
